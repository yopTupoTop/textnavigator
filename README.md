# TextNavigator — проверка условий договоров поставки

## 1. Назначение и пользователь

Локальное приложение для **специалиста по закупкам**, который сверяет условия поставок и не хочет перечитывать цепочку «договор + допсоглашения + письма».
Из загруженных TXT-файлов оно строит таблицу договоров (номер, поставщик, сумма в рублях, срок поставки, неустойка на выбранную дату проверки)
и для каждого значения показывает **источник**: файл, абзац, точную цитату, позиции в тексте и статус документа, на основании которого принято решение.

## 2. Основные сценарии

1. Загрузить несколько TXT-файлов (договоры, допсоглашения, письма, проекты) → получить таблицу действующих условий.
2. Выбрать договор → увидеть действующие сумму, срок, неустойку, что и каким документом изменено, историю значения.
3. Нажать «Перейти к абзацу» → увидеть исходный документ с подсвеченной цитатой.
4. Посмотреть блок предложений об изменении условий (письма, проекты, ещё не вступившие в силу соглашения) — они условия не меняют.
5. Задать один из четырёх готовых запросов: срок на дату проверки, сумма договора, договоры без суммы в тексте, договоры с несогласованными изменениями срока.
6. Сменить дату проверки — набор действующих допсоглашений пересчитывается.

## 3. Установка и запуск

Нужен Python 3.10+.

```bash
pip install -r requirements.txt     # streamlit, pytest
streamlit run app.py                # откроется http://localhost:8501
python3 -m pytest                   # тесты
```

Разрабатывалось на Python 3.13 и Streamlit 1.66. Папка `documents/` — учебные материалы задания, используются только тестами; приложение работает с файлами, загруженными через интерфейс.

## 4. Зависимости и технологии

* Ядро (`textnav/`): только стандартная библиотека Python, регулярные выражения. **LLM и платные API не используются.**
* Интерфейс: Streamlit (подтягивает pandas). Тесты: pytest.

## 5. Пример использования

1. `streamlit run app.py`, в верхнем поле загрузить файлы (можно перетащить сразу все).
2. В боковой панели указать дату проверки.
3. Для учебного набора из `documents/` на 10.03.2026 получается:

| Договор | Сумма | Срок | Неустойка | Статус |
|---|---|---|---|---|
| STN-101 | 1 380 000 ₽ (допсоглашение № 1) | 30.04.2026 (было 15.04.2026) | 0,1% в день, не более 10% | Подтверждено |
| STN-102 | 840 000 ₽ | 20.03.2026 | 0,05% в день, не более 5% | Подтверждено |
| STN-103 | Нет данных | 30.04.2026 | Нет данных | Неполные данные |

Несогласованные предложения: STN-101 (проект № 2: 1 450 000 ₽ и срок 10.05.2026), STN-102 (письмо: срок 27.03.2026).

## 6. Архитектура

```
TXT → loader → segmenter → classifier → linker → extractor → resolver → app.py (Streamlit)
       чтение    абзацы     тип и        привязка   правила    применение    таблица, детали,
                 + позиции  статус по    по номеру  (regexp)   допсоглашений источник, запросы
                            тексту       в тексте              + предложения
```

| Модуль | Роль |
|---|---|
| `loader.py` | чтение TXT (UTF-8, cp1251); имя файла — только для показа |
| `segmenter.py` | абзацы: номер, строка, позиция в файле |
| `classifier.py` | тип (договор / допсоглашение / проект / письмо) и статус по содержимому, дата вступления в силу, стороны |
| `linker.py` | привязка документов к договорам по номеру в тексте |
| `extractor.py` | сумма, срок, неустойка, поставщик, предложения, пункты «изложить в редакции» |
| `resolver.py` | какие документы вправе менять условия; хронологическое применение; конфликты |
| `patterns.py` | регулярные выражения и разбор чисел/дат |
| `models.py` | модель данных |
| `pipeline.py` | точка входа `analyze(files, as_of)` |

**Модель данных:** `Document → Paragraph`; `Evidence(file, paragraph, line, quote, start, end, doc_start, doc_end, doc_status)`;
`FieldValue(state, value, evidence, history, original)`; `Proposal`; `ContractResult`. Состояния: Подтверждено / Нет данных / Требуется проверка; у договора ещё «Неполные данные».

## 7. Три ключевых технических решения и компромиссы

1. **Правила и регулярные выражения вместо LLM.** Воспроизводимо, бесплатно, цитата — прямое доказательство. Но хрупко к новым формулировкам и не понимает смысл; нужна расширяемая библиотека шаблонов.
2. **Допсоглашение = «замена пункта» с повторным запуском тех же экстракторов.** Единый код для договора и изменений, понятная история значения. Не покрывает «исключить», «дополнить», изменения без «изложить в редакции» — такие случаи уходят в «Требуется проверка».
3. **Консервативность: «Нет данных» / «Требуется проверка» вместо догадки.** Исключает выдуманные значения; цена — часть случаев уходит человеку.

## 8. Допущения

Дата проверки задаётся явно (по умолчанию в интерфейсе — 10.03.2026 из задания). Допсоглашение действует с даты вступления в силу, а не подписания.
Письма, проекты, неподписанные и ещё не вступившие в силу соглашения условия не меняют. «Подписано обеими сторонами» берётся из строки «Статус:».
Все суммы в рублях. Несколько соглашений применяются хронологически. Тип документа, привязка и приоритет не зависят от имени файла, даты файла и даты загрузки.
Четыре запроса из задания реализованы в обобщённом виде (с выбором договора), чтобы в интерфейсе не было вшитых номеров договоров.

## 9. Пять вопросов клиенту

1. Какие форматы реально приходят (PDF, сканы, DOCX, ЭДО), сколько документов на договор в среднем, где они хранятся?
2. Сколько типовых шаблонов договоров и допсоглашений, какие формулировки сумм и сроков самые частые? Можно получить 30–50 размеченных примеров?
3. Какие поля нужны помимо суммы, срока и неустойки (оплата, этапы, НДС, валюта) и какие решения принимаются по этим данным?
4. Какова цена ошибки и допустимая доля «Требуется проверка»: лучше пропустить значение или показать его с риском?
5. Кто какие договоры вправе видеть (подразделения, коммерческая тайна) и должен ли результат попадать в ERP/СЭД?

## 10. Две метрики

* **Точность подтверждённых значений:** доля полей (сумма, срок, неустойка), где значение верно *и* цитата его содержит, на размеченной выборке реальных договоров; отдельно — доля «уверенных» ошибок (значение выдано, а правильно было «Требуется проверка»), цель ≈ 0.
* **Время сверки договора** (медиана до/после внедрения) и доля значений, подтверждённых закупщиком по цитате без открытия всего документа.

## 11. Масштабирование до 100 000 документов

Обработка при загрузке, а не при каждом действии пользователя: очередь задач и воркеры, хранилище файлов, реляционная БД для договоров, версий документов, извлечённых полей с цитатами и позициями.
Версия правил извлечения хранится вместе с результатом (переобработка при изменении правил). Привязка по номеру → реестр договоров и контрагентов с обработкой коллизий номеров.
Поиск кандидатов — полнотекстовый индекс (Postgres FTS или OpenSearch). Пересчёт «на дату» — по сохранённым фактам (даты вступления, статусы), а не повторным разбором текста.
Для файловых форматов — отдельный конвейер (парсинг, OCR) с оценкой качества распознавания.

## 12. Права доступа

Права на уровне договора и связанных документов (ACL из СЭД/SSO). Фильтрация **до** поиска, агрегатов и построения таблицы, чтобы значения и цитаты не утекали через общие индексы и кэш.
Журнал просмотров и экспорта, разделение ролей (закупщик, юрист, администратор), цитаты показываются только при наличии прав на исходный документ.

## 13. Три следующих улучшения (по приоритету)

1. Размеченная выборка реальных договоров и автоматический расчёт метрик при каждом изменении правил; расширение формулировок и полей (оплата, этапы, НДС, другие формы ставки неустойки).
2. Очередь «Требуется проверка» с подтверждением человеком (принять/исправить, сохранить решение и цитату), экспорт реестра.
3. Резервный слой на модели (локальной или по подписке заказчика) только для нераспознанных пунктов, с обязательной дословной цитатой, проверяемой кодом; затем PDF/DOCX/OCR.

## 14. Ограничения текущей реализации

* Только TXT (UTF-8/cp1251), только рубли, одна сумма, один срок и одна ставка на договор; этапы, частичные поставки и валюта не поддержаны.
* Распознаются формулировки вида «составляет … рублей», «не позднее ДД.ММ.ГГГГ», «Пункт X договора изложить в редакции: «…»»; свободный текст, таблицы и сканы — нет.
* Допсоглашения, которые исключают или дополняют пункты, не применяются и уходят в «Требуется проверка».
* Сумма прописью не сверяется с цифрами.
* Подписание определяется только по строке «Статус:»; подпись в виде реквизита в другом месте не распознаётся.
* Интерфейс пересчитывает результат при каждом действии (для больших наборов нужно кэширование); нет аутентификации и хранения — локальное приложение.
* Таблица Streamlit отрисовывается на canvas, поэтому автоматически читать её значения из HTML нельзя; её проверяли визуально.

## 15. Отчёт о вайбкодинге

**AI-инструмент.** Claude Code (агентная среда: ИИ сам читает файлы, пишет код, запускает команды, тесты и браузер). Модель по настройке сессии — `claude-sonnet-5-5`; какая модель отвечала на каждом шаге, по самой сессии надёжно не видно — сверить по истории чата.
Код написал ИИ; моя роль — постановка этапов, согласование архитектуры, ревью результатов.

**Как это шло.** Разработка велась по шести запросам (полный дословный текст — в [PROMPTS.md](PROMPTS.md)), между ними — короткие ответы «согласовано» и «да».
Эта версия проекта написана **заново** (отдельная папка) в том же чате, где раньше уже собирался первый прототип с другим интерфейсом; ИИ видел тот прототип, поэтому часть решений и регулярных выражений закономерно похожа. Первый прототип в этот проект не входит.

**Характерные запросы**
1. *Этап 1:* «…До написания кода: определи тип каждого документа… найди изменения условий и проверь их юридический статус… На этом этапе не пиши код. Сначала представь результаты анализа и архитектурное решение.» → ИИ показал таблицы анализа 6 документов, архитектуру, модель данных и список тестов и ждал согласования.
2. *Этап 2:* «…Для каждого извлеченного значения сохраняй: значение, имя файла, точную цитату, номер абзаца, начальную и конечную позиции, статус документа… При конфликте или недостаточной уверенности возвращай статус "Требуется проверка". Не используй LLM API.» → модуль обработки с цитатами и координатами.
3. *Этапы 4–5:* «Запусти весь набор тестов, проанализируй ошибки, исправь их и повтори запуск» и «Если обнаружишь зависимость от исходных данных, исправь архитектуру, а не добавляй исключения для конкретного файла» → тесты, мутационная проверка и динамическая проверка на изменённой копии договора.

**Примеры ошибок ИИ**
* В комментариях `patterns.py` остались примеры значений из документов («1 200 000», «15.04.2026»). Нашёл тест на вшитые значения; комментарии обезличены.
* Часть первых тестов была слабой: при намеренной поломке правил (применять неподписанные допсоглашения, убрать исключения аванса/оплаты) они продолжали проходить, потому что тестовые формулировки не доходили до защиты. Нашёл при мутационной проверке; добавлены тесты на формулировки, которые реально доходят до этих правил.
* У договора без суммы (STN-103) общий статус сначала был «Подтверждено», что вводило в заблуждение. Исправлено: добавлен статус «Неполные данные».
* В интерфейсе в первой версии не помещались колонки таблицы, а подписи кнопок обрезались. Нашёл по скриншоту страницы в браузере; компоновка исправлена.

**Способы проверки и исправления:** запуск модуля на 6 документах и сверка с ручным анализом из этапа 1; pytest с временными копиями файлов (оригиналы не меняются); проверка, что цитата и координаты — точная подстрока абзаца и файла; тест на отсутствие вшитых значений; мутационная проверка (ломаются правила в копии кода, тесты должны упасть); прогон интерфейса в браузере через реальную загрузку файлов; динамическая проверка на изменённой копии договора с произвольным именем.

**Заполняется по факту (не придумывать):**
* Фактические затраты времени: ___ ч ___ мин (лимит 4 ч).
* Что сделано мной лично, а что ИИ (по моей оценке): ___.
* Результат запуска тестов на моей машине (`python3 -m pytest`): ___.
* Оставшиеся задачи по итогам моей проверки: ___.
